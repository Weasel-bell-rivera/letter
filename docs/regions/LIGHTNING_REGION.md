# 雷之区域

## 区域定位

雷之区域是世界中的隐藏元素区域。

玩家不会在常规区域入口或默认主流程中直接看到该区域。区域入口、发现方式、解锁条件、与现有房间的连接关系及进入后是否永久开放均为待确认内容；在这些规则写入 `docs/maps/MAP.md` 与 `docs/maps/WORLD_PROGRESSION.md` 前，不得创建正式入口或实现区域解锁逻辑。

本区域必须围绕雷电主题建立独立的视觉、环境行为和谜题语言，不能只通过替换颜色、背景或危险物外观与其他区域区分。

## 核心体验目标

- 让玩家感到自己发现了主路径之外的异常空间。
- 使用清晰、可预测的因果关系表现雷电，而不是依赖不可判断的随机伤害。
- 通过短暂状态、传导关系与时序变化产生观察、推导和顿悟。
- 保持失败后可以快速、无惩罚地重新尝试。
- 隐藏性只影响区域的发现方式，不降低机关反馈和玩法规则的可读性。

## 氛围与视觉方向

关键词：

- 隐秘
- 异常
- 蓄势
- 瞬发
- 高能
- 冷峻
- 精密

候选视觉元素包括：

- 远处闪电与短暂照明
- 带有明确走向的导电结构
- 蓄电装置、避雷设施与绝缘材料
- 被雷击破坏或熔蚀的遗迹
- 在暗色环境中用于提示状态的高亮电弧
- 雷暴云、雨幕与高空设施

可交互、危险、已充能和未充能状态必须具有彼此可区分的视觉表现。装饰性闪电不得与会影响玩法的雷击使用相同反馈。

以上内容仅定义美术与体验方向，不批准任何具体玩法行为。

## 玩法语言候选

下列内容均为候选概念，不是正式规则，也不得进入正式房间实现：

| 候选机制 | 可能的谜题作用 | 状态 |
|---|---|---|
| 固定节奏雷击 | 形成可观察的通行窗口 | 待确认 |
| 电力传导 | 在显式连接的装置之间传递状态 | 待确认 |
| 蓄电与放电 | 延迟触发机关或改变时序 | 待确认 |
| 导体与绝缘体 | 控制电力路径或安全空间 | 待确认 |
| 雷电驱动机关 | 将电力状态转换为门、平台或其他机关信号 | 待确认 |
| 短暂照明 | 暴露路径、符号或机关状态 | 待确认 |

候选机制不得采用不可观察的随机时序。任何周期、范围、目标选择或传播路径都必须能让玩家在行动前判断结果。

## 镜子与镜像约束

雷电对 Player、MirrorClone 和已放置镜子的作用尚未批准。

在批准雷区机制前，必须逐项明确：

- 雷击命中 Player 时是否沿用 Player 死亡与完整房间重置规则。
- 雷击命中 MirrorClone 时是否沿用镜像死亡与镜子自动回收规则。
- 雷电是否能够破坏已放置镜子。
- 镜子是否参与导电、反射、蓄电或改变雷击目标。
- Player 与 MirrorClone 是否遵循完全相同的导电和机关触发规则。
- 特殊墙壁镜、旋转重力镜像与雷电环境的交互方式。
- 镜像被回收或死亡时，相关导电、蓄电和机关占用如何清除。

未经批准，不得让雷电改变既有镜像输入映射、重力、生成位置、碰撞或镜子放置规则。任何新增的镜子或镜像行为都必须同步更新 `docs/MIRROR_MECHANIC.md` 和相应测试。

## 隐藏区域规则

已确认：

- 雷之区域是隐藏区域。
- 本区域不作为当前默认主流程中直接可见的常规元素区域入口。

待确认：

- 隐藏入口所在的现有房间及连接方向。
- 发现入口所需的观察、解谜或收集条件。
- 是否要求完成一个或多个主要元素区域。
- 首次发现后，入口是否永久可见或永久开放。
- 解锁状态是否写入长期存档。
- 离开区域后如何再次进入。
- 雷之区域是否属于可选挑战、隐藏叙事内容或结局条件。
- 区域规模、房间编号范围和首个房间编号。

上述内容确认后，必须同步更新 `docs/maps/MAP.md`、`docs/maps/WORLD_PROGRESSION.md`、雷区 `ROOM_INDEX.md` 以及涉及入口的房间文档。

## 房间与难度结构

区域房间数量和正式教学顺序尚未确定。后续设计应至少区分：

1. 发现段：建立隐藏区域的异常感，并安全展示首个已批准规则。
2. 理解段：让玩家独立预测雷电的时序或传播结果。
3. 镜像组合段：在不改变核心镜像规则的前提下组合雷区机制。
4. 精通段：减少显式提示，组合多个已经分别教学的规则。
5. 收束段：综合区域知识，并明确该隐藏区域的完成结果。

不得因为区域隐藏而默认采用高难度。难度仍需通过机制教学逐步建立。

## 实现约束

- 当前没有已批准的雷区专属机制，不得创建雷区正式玩法实现或正式房间 Scene。
- 区域专属机制必须先在本文记录完整规则和批准状态，再进入原型或正式开发。
- 通用机制不得写死在雷区具体房间脚本中。
- 具有运行时状态、交互、移动、重置或生命周期的雷区对象应使用通用组件和 Prefab。
- 不得通过对象名称、Tile 名称、Sprite 名称、Tilemap 名称或房间编号推断导电、危险、绝缘或镜子放置语义。
- 新增表面语义或运行时修改 Tilemap 的机制前，必须更新对应权威系统文档并明确碰撞、重置、存档、镜子和场景切换规则。
- 雷击、传导和蓄电如包含周期或计时，必须使用与帧率无关的确定性逻辑。
- Player 死亡、手动重置、MirrorClone 死亡或回收以及场景切换时的状态清理必须在机制批准时逐项定义。
